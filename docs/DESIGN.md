# quarry design

This document explains how quarry works and why it is built the way it is. Sections are added as
each part of the engine lands.

## Text analysis

Documents and queries go through the same analyzer (`internal/analysis`), so a query term matches
the same form of the word in a document. The goal is to match the analyzer Anserini uses for its
BM25 baselines (`DefaultEnglishAnalyzer`, Lucene 10.5), so that our scores are directly comparable
to the published numbers.

The pipeline, in order:

1. **Tokenize** following Lucene's `StandardTokenizer`, a simplified form of Unicode word
   segmentation (UAX #29):
   - Letters and digits form words, and may be adjacent (`cd4`, `1990s`).
   - `.` `'` `:` stay inside a word when they sit between two letters (`u.s.a`, `don't`).
   - `.` `,` `;` `'` stay inside a number when they sit between two digits (`3.5`, `1,000`).
   - `_` joins word parts (`foo_bar`). Combining marks stay attached (`é` written as `e` + accent).
   - Chinese characters and Hiragana become one token per character. Roman numerals (`Ⅳ`) and
     circled letters (`Ⓐ`) count as letters.
   - `©`, `®`, and `™` become tokens of their own, keeping a following emoji selector (`©️`).
   - A token is matched within at most 255 characters. A longer run is cut at the last point in
     that window where a token may end, and scanning resumes right after it, so a stray `.` or
     accent at the cut is dropped, as in Lucene.
   - A Hebrew letter may keep a trailing `'`, and two Hebrew letters may be joined by `"`
     (`ו"ל`), following the same unit rules as Lucene's grammar.
2. **Remove a possessive** `'s` (also with `’` or `＇`): `dog's` becomes `dog`.
3. **Lowercase** each character.
4. **Remove stopwords**: Lucene's 33-word English list (`a`, `the`, `of`, ...).
5. **Stem** with the classic Porter (1980) algorithm: `running` becomes `run`,
   `generalization` becomes `gener`. This is Martin Porter's original algorithm, not the later
   "Porter2" that most Snowball libraries call English; the two disagree on about 5% of words.

### Why our own Porter stemmer

We first used an existing Go library. Checking it against real Lucene on every word of one to four
letters from a 16-letter alphabet (69,904 words) showed it panicked on `eed`, `eeds`, and `eing`
(`eed` appears 4 times in the SciFact and NFCorpus corpora) and disagreed with Lucene on `ies` and
`sses`. A panic on a user's query would take down a server, so quarry has its own implementation in
`internal/analysis/porter.go`. It matches Porter's published 23,531-word test vocabulary and Lucene
on all 69,904 words.

### How we know it matches Lucene

`scripts/lucene-oracle/LuceneAnalyze.java` runs Lucene's real analysis chain.

- **In CI:** `internal/analysis/testdata/golden_inputs.txt` holds hand-written tricky inputs, and
  `golden_lucene.txt` holds Lucene's output for each one, generated by `scripts/lucene-golden.sh`.
  CI checks our analyzer against it without needing Java.
- **One-time full check:** our output was compared with Lucene's token by token on every document
  and test query of SciFact and NFCorpus. Every line matches except one SciFact document (see below).
  Our total term counts are 838,126 (SciFact) and 637,485 (NFCorpus); Anserini's published index
  statistics are 838,128 and 637,485.
- **Randomized check:** 10,000 random strings built from the tricky characters above (mid
  characters, accents, symbols, Hebrew, Han, runs of up to 300 repeated characters) were compared
  with Lucene. Every mismatch falls into one of the known differences below.

### Known differences from Lucene

| Difference | Effect on our benchmarks |
|------------|--------------------------|
| Emoji (other than `©` `®` `™`) are dropped; Lucene keeps them as tokens, including multi-character sequences such as flags, skin tones, and a zero-width joiner before a symbol. Go's standard library has no Unicode emoji property table. | 2 tokens (`↔`, in one SciFact document) out of 838,128 |
| Character classes come from Go's Unicode categories, not the exact word-break property tables. Katakana next to other letters stays in one token (Lucene splits it), and `〆` is kept (Lucene drops it). | None observed |
| A run of 255 or more underscores: Lucene's fixed-size scan buffer produces odd tokens here (for example, a token of only underscores). We do not imitate this. | None observed |
| The 255 limit counts characters; Lucene counts UTF-16 units, so they differ only for characters outside the Basic Multilingual Plane. The same applies to the Porter stemmer's rule of leaving words of one or two characters unchanged. | None observed |

## Scoring

BM25 with Lucene's IDF, `ln(1 + (N - df + 0.5) / (df + 0.5))`, and the Lucene 8+ term score
`idf * tf / (tf + k1 * (1 - b + b * dl / avgdl))`, with k1 = 0.9 and b = 0.4 (Anserini's defaults).

### Known difference from Lucene

Lucene stores each document's length in one byte: lengths up to 40 are exact, and longer ones are
rounded down (100 is stored as 96, 300 as 280). It also scores in 32-bit floats. quarry uses exact lengths and 64-bit floats. With identical analysis, this
is the likely reason SciFact nDCG@10 is 0.6777 against Anserini's 0.6789 while Recall@100 and
Recall@1000 match exactly: the same documents are retrieved, and a few near-ties are ordered
differently.

## On-disk index format

`quarry-index` saves an index as a directory of six files (format version 2), or eight with
`--store-text`. An index from another
version fails to open with a message to rebuild it. All integers are
little-endian. Each binary file starts with an 8-byte header, a 4-byte magic string and the format
version, so a file from another format or version is rejected with a clear error.

```text
manifest.json   format_version, doc_count, total_terms, term_count, bm25_k1, bm25_b,
                and for each binary file: its size and CRC32C checksum (written last)
seg0.dict       "QDCT" v2 | termCount u32 | termCount x 36-byte entries | term bytes
                entry: termOffset u32, termLen u32, docFreq u32, postingsOffset u64, postingsLen u32,
                       skipOffset u64, maxScore f32
seg0.post       "QPST" v2 | each term's postings, in dictionary order
                posting: uvarint(docID gap), uvarint(tf); the first gap is the doc ID itself
seg0.skip       "QSKP" v2 | for each term, one 12-byte entry per block of 128 postings
                entry: lastDocID u32, offset u32 (from the term's first posting), blockMax f32
seg0.lens       "QLEN" v2 | docCount u32 | docCount x u32 document lengths
seg0.ids        "QIDS" v2 | docCount u32 | (docCount + 1) x u64 offsets | external ID bytes
seg0.text       "QTXT" v2 | each document's text, in doc ID order          (only with --store-text)
seg0.toff       "QTOF" v2 | (docCount + 1) x u64 offsets into the text     (only with --store-text)
```

How a lookup uses the files, for one term with 300 postings (3 blocks):

```text
seg0.dict  binary search by term
   row: docFreq=300  maxScore  postingsOffset ---------------+   skipOffset --+
                                                              |                |
seg0.skip                                                     |                v
   [lastDoc  offset=0    blockMax] [lastDoc  offset=a  blockMax] [lastDoc  offset=b  blockMax]
                 |                               |                           |
seg0.post        v                               v                           v
   ... | block 0: 128 (gap, tf) varints | block 1: 128 varints | block 2: 44 varints | ...
                                                                       (offsets count from postingsOffset)
seg0.lens  doc ID -> length (BM25)        seg0.ids  doc ID -> external ID (results)
```

Choices and tradeoffs:

- **Fixed-width dictionary entries, sorted by term.** Finding a term is a binary search over equal-sized
  rows, with no parsing and no in-memory map to build at startup. Terms live in a separate blob so
  rows stay fixed-width. Front-coded blocks or an FST would be smaller, but are more complex.
- **Delta + varint postings.** Doc IDs are stored as gaps from the previous doc ID. Gaps are small for
  common terms, so most take one byte.
- **Blocks of 128 with skip entries.** A term's postings are one gap-encoded stream, cut into blocks of
  128. Each block's skip entry holds its last doc ID and where it starts, so decoding a block needs only
  the previous block's last doc ID, and `Advance(target)` binary-searches the skip entries and decodes
  one block instead of the whole list. Because blocks are pieces of the same stream, the postings file
  is byte-for-byte what format 1 wrote; only the skip file and wider dictionary rows are new. Bit-packed
  blocks (as in Lucene) would be smaller and faster to decode, but are a separate codec.
- **Score bounds for pruning.** Each skip entry stores the block's highest BM25 contribution, and each
  dictionary row the term's highest. They are computed with the final index's document count, average
  length, and document lengths, exactly as a query computes scores, then rounded up to float32, so a
  bound is never below a real score. The manifest records k1 and b, since the bounds are only valid for
  those parameters. WAND uses the term bounds and Block-Max WAND the block bounds.
- **Strict decoding.** The decoder returns an error, never panics, on truncated input, values over
  32 bits, a zero gap after the first posting, a zero term frequency, a non-minimal varint, or
  leftover bytes. It is fuzz tested.
- **Checked on open.** Every file's size and CRC32C must match the manifest, and every table offset is
  bounds-checked, so a corrupt or partly written index fails at open instead of returning wrong results.
  The manifest is written last, so an interrupted build has no manifest and is rejected.
- **No overwrites.** `quarry-index` refuses to write into an existing directory.
- **Stored text is optional and separate.** Search never reads it, so it is off by default and the
  other files are byte-identical with or without it. Documents arrive at the builder in doc ID
  order, so their text is appended to `seg0.text` (and each end offset to `seg0.toff`) as it is
  added: no text stays in memory, and it skips the chunks and the merge entirely. The offsets go in
  their own file because their count is only known at the end. An index with text has seven binary
  files in its manifest; a build that predates stored text rejects it, because it expects five.
  The cost is disk and startup: MS MARCO's text is 2.98 GB, and checksumming it on open makes
  `quarry-serve` take about 7 s to start.

### Memory-mapped reads

`Open` memory-maps the four binary files (`mmap`, read-only) instead of copying them into the Go heap.
Lookups read the mapped bytes directly. The operating system loads each 16 KB page (4 KB on most Linux
machines) the first time it is touched, and keeps it in its page cache, which is shared memory it can
evict and reload from disk when it needs room.

What this means in practice:

- **The Go heap stays small.** An index larger than free RAM can still be opened. Only the pages a query
  touches need to be in memory, and the OS decides which ones to keep.
- **Warm and cold queries differ.** The first query that touches a page waits for a disk read; later ones
  hit the page cache. Benchmarks must say whether the cache was warm.
- **Opening still reads every byte once,** because checksums are verified on open. That leaves the files
  in the page cache, which helps the first queries. For a very large index, open time is then bounded by
  disk speed; skipping or deferring verification is a possible later option.
- **Nothing returned points into the mapping.** Postings are decoded into new memory and external IDs are
  copied into strings, so results stay valid after `Close` unmaps the files.
- **The files must not change while mapped.** Indexes are immutable, and `quarry-index` never overwrites
  one. Truncating a mapped file would crash the reader.
- **Unix only.** mmap uses the standard `syscall` package on macOS and Linux. On other platforms `Open`
  returns an error instead of silently reading the files into memory.

Measured with `go test ./internal/index -run '^$' -bench Open -benchtime 20x -count 5` (Apple M3, warm
cache, synthetic 100,000-document index of 10.7 MB): opening went from 3.1 ms and 10.7 MB of heap per
open (reading the files) to 1.75 ms and 5.4 KB (mapping them, including closing). On the 2 MB SciFact
index, end-to-end search and evaluation time and peak memory did not measurably change.

Searching a saved index gives exactly the same results as the in-memory index: the same documents and
bit-identical scores. This is checked on 200 random corpora in the tests, and the run files for SciFact
and NFCorpus are byte-identical.

## Indexing within a memory budget

`quarry-index` uses single-pass in-memory indexing (SPIMI). It collects postings for a chunk of
documents in memory, and when an estimate of the chunk's memory reaches `--mem-budget`, it writes the
chunk as a temporary segment (`tmp-seg0`, `tmp-seg1`, ... inside the output directory) and starts a new
chunk. At the end, a k-way merge combines the segments into the final single-segment index, and the
temporary segments are deleted. If everything fits in the budget, the index is written directly.

Why SPIMI rather than sort-based indexing (BSBI): BSBI maps every term to a global integer ID, writes
(termID, docID, tf) triples, and sorts them, so it must keep the whole term-to-ID map in memory and
sort far more records than there are postings lists. SPIMI appends postings straight to each term's
list in a per-chunk hash map, needs no global term IDs, and sorts only each chunk's terms once at
flush. The cost is that a chunk's memory depends on its vocabulary, which is why the budget is an
estimate (below) rather than a fixed record count.

- **Doc IDs need no remapping.** Documents get IDs in input order, and each chunk holds a contiguous
  range. A segment stores IDs from 0, and the merge adds the segment's starting ID. Because ranges never
  overlap and only increase, a term's postings from several segments are simply joined in segment order.
- **The merge is over terms, not postings.** Each segment's dictionary is sorted, so a min-heap holding
  one cursor per segment yields terms in global order. Ties go to the earlier segment.
- **One writer for both paths.** A streaming segment writer takes terms in sorted order and writes their
  postings immediately; only the 24-byte dictionary rows and term bytes are kept until the end. The
  single-pass write and the merge both use it, so the output is byte-identical for any budget. Tests
  check this on random corpora at several budgets, and SciFact and NFCorpus built with budgets from 16 KB
  (1,849 segments) to 1 GB (no segments) are byte-identical to a single-pass build.
- **Temporary segments skip `fsync`.** They are deleted after the merge, and a crash before the final
  manifest leaves an index that `Open` rejects, so syncing them buys nothing. On macOS, Go's `Sync` is a
  full flush to the drive, so skipping it matters.
- **A failed build cleans up.** `quarry-index` removes its partial output directory on any error.

How the budget bounds the whole build:

- **The chunk gets a third of the budget.** The rest is headroom for the garbage collector, the analysis
  pipeline, and writing segments.
- **The budget is Go's soft memory limit** (`debug.SetMemoryLimit`) from 256 MB up, unless a lower
  `GOMEMLIMIT` is set. By default Go lets the heap grow to about twice the live data before collecting;
  with a limit it collects more often as the heap nears the budget. The limit must sit well above the
  live chunk: with a 1 GB chunk under a 1 GB limit, the collector ran almost constantly and the build
  took 130 s instead of about 72 s. Smaller budgets only size chunks, which tests use to force many segments.
- **The estimate is measured, not guessed.** Per document it counts 40 bytes plus the ID, per posting 10
  bytes (8 bytes plus spare capacity from slice growth), and per new term 96 bytes plus the term. These
  were fitted against the live heap after garbage collection on chunks of SciFact repeated 20 times and of MS MARCO: the old
  constants (64, 8, 20) read 19 to 25% low on large chunks; the new ones read 2 to 10% high, so chunks
  flush slightly early.
- **The merge is outside the chunk.** It holds one dictionary row per distinct term (about 100 MB for MS
  MARCO's 2.66 million terms), one decoded postings list at a time, and a mapping per segment. That fixed
  cost is why a 256 MB budget used 297 MiB on MS MARCO, while 512 MB and up stayed within budget.
- **Memory is measured as peak footprint.** On macOS, Go returns memory with `MADV_FREE_REUSABLE`, and
  those pages stay in the resident set size until the system reclaims them; at 256 MB, RSS read 1.33 GB
  while the footprint was 0.29 GB. On Linux, Go returns memory with `MADV_DONTNEED`, so RSS drops right
  away, but RSS there also counts pages of the memory-mapped segments the merge reads. Linux has not been
  measured.

## Parallel text analysis

Profiling a sequential build of SciFact repeated 20 times (wall clock per phase) showed analysis at
about 78% of the time, adding postings at about 18%, and JSON decoding at about 3%. So only analysis
runs in parallel, as a pipeline inside `corpus.Read`:

- **One reader goroutine** decodes records in order. It sends each record to a shared `jobs` channel
  for the workers, and also to an `ordered` channel that keeps input order.
- **`--workers` goroutines** analyze records from `jobs`. Each record carries its own result channel
  with room for one value, so a worker never waits to hand back a result.
- **The calling goroutine** takes records from `ordered`, waits on each record's own result channel,
  and passes the terms to the index builder. Records reach the builder in input order, so doc IDs and
  the index bytes do not depend on the worker count, and the builder needs no locks.
- **Memory stays bounded.** `ordered` holds at most 16 records per worker, so a slow record stalls the
  reader instead of letting finished results pile up.
- **Errors keep their order.** A decoding error travels through `ordered` like a record, so the
  builder sees exactly the records it would have seen sequentially before the error. On any error,
  `Read` closes a `done` channel and waits for every goroutine to exit before returning.

- **Two input formats share the pipeline.** BEIR JSONL and MS MARCO style TSV (`id<TAB>text`, chosen by
  the `.tsv` extension) differ only in the function that produces the next record. The TSV reader
  copies each ID with `strings.Clone`: a substring shares its parent's memory, so an index that kept
  substring IDs would also keep every full passage alive. On MS MARCO that cost about 1.2 GB of peak
  memory (3.9 GB versus 2.7 GB).

The alternative was sharded accumulators: each worker builds its own partial index, merged at every
flush. That would also parallelize adding postings, but doc IDs must still follow input order and the
memory budget would be split across shards. With the pipeline, decoding and adding postings remain
sequential (about 2.3 s of the 10.5 s sequential build), which limits the speedup to about 4.4x; 8
workers measured 4.2x (README, Indexing speed). Sharding is worth revisiting if adding postings
becomes the bottleneck.

## Query processing

A query is analyzed like a document, then repeated terms are merged into one term with a count
(Anserini boosts a repeated term the same way). Queries are disjunctive (OR): a document matching
any term is a candidate. All three algorithms in `internal/query` share one interface,
`Search(algo, index, bm25, terms, k)`, and must return exactly the same results.

### Top-k heap and tie-breaking

`TopK` is a min-heap of at most k results, with the worst kept result at the root. A new result
replaces the root only if it ranks strictly better, so each candidate costs O(log k) and memory is
O(k) no matter how many documents match. "Better" means a higher score, then a lower doc ID, which
makes every ranking deterministic. `Threshold` returns the root's score only once the heap is full;
until then nothing can be pruned. At the end the heap is copied and sorted.

Every algorithm visits documents in increasing doc ID order. A later document with a score equal to
the threshold therefore loses the tie, so pruning may skip anything whose bound does not strictly
exceed the threshold.

### Exhaustive document-at-a-time

The reference algorithm. It opens one cursor per query term, then repeatedly takes the smallest
current doc ID across cursors, adds the BM25 contribution of every cursor on that document, offers
the sum to the heap, and moves those cursors with `Next`. Every matching document is scored, so its
cost grows with the total length of the query's postings lists.

### WAND

WAND (Broder et al., 2003) uses each term's stored `maxScore`, times its query count, as an upper
bound on what the term can add to any document. Each step:

1. Sort cursors by current doc ID (ties by term order). An insertion sort over pointers is used,
   because only a few cursors move per step.
2. **Find the pivot:** add up bounds from the first cursor on, and stop at the first cursor where the
   running sum could beat the threshold. That cursor's doc ID is the pivot. If no prefix can beat
   it, no remaining document can enter the heap, and the search ends.
3. If the first cursor is already on the pivot, every cursor before the pivot is too: score the
   pivot document fully and move the cursors on it with `Next`.
4. Otherwise, move one cursor before the pivot (the one with the largest bound) straight to the
   pivot with `Advance`, which binary-searches the skip entries and decodes one block.

Why it is safe: a document before the pivot can only contain terms from cursors before the pivot
(the others are already past it), and their bounds add up to no more than the threshold.

### Block-Max WAND

Per-term bounds are loose: one very short document with a high term frequency sets `maxScore` for
the whole list. Block-Max WAND (Ding and Suel, 2011) also checks the per-block bounds from the skip
file. After WAND picks the pivot, it extends the prefix to every cursor on the pivot document, and:

1. **Shallow advance** each prefix cursor to the block containing the pivot. This moves only a
   block pointer over skip entries; no postings are decoded and the cursor's position does not move.
2. Sum the block bounds of those blocks. Also compute `next`: the earliest end of those blocks plus
   one, capped at the doc ID of the first cursor outside the prefix.
3. If the block bound cannot beat the threshold, no document in `[pivot, next)` can win: only
   prefix terms can occur there, each within its current block. Move one prefix cursor (the largest
   bound) to `next` and repeat, without scoring anything.
4. Otherwise, continue exactly like WAND step 3 or 4.

### Why the results are exact

Pruning only ever skips documents whose upper bound cannot strictly beat the k-th score, so the top
k cannot change. Three details make that true in floating point, not just on paper:

- **Bounds are rounded up** to float32 when the index is built, from the same float64 formula
  queries use, so a stored bound is never below a real score.
- **Scores are summed in one order.** Every algorithm adds term contributions in sorted term order,
  so a document gets bit-identical float64 scores from all three.
- **A 1e-9 relative margin** on every bound comparison covers summing bounds in a different order
  than scores. It can only cause extra scoring, never a skip.

Bounds are only valid for the BM25 parameters used to build them, so WAND and BMW refuse a query
whose k1 or b differ from the index's manifest; exhaustive search accepts any. Randomized tests
compare all three on random corpora (in memory and on disk), and the MS MARCO run files of all
three algorithms are byte-identical.

### What pruning costs

At k=10 the threshold rises fast and most documents are skipped: on MS MARCO, BMW's mean latency
is 7.04 ms against 26.75 ms for exhaustive search. At k=1000 the heap fills slowly and the
threshold stays low, so far less is skipped and the per-step bookkeeping (sorting cursors, finding
the pivot, checking blocks) shows: WAND takes 18.10 ms and BMW 19.46 ms. BMW's extra block checks
pay off only when they let it skip. BMW is the default because short result lists (k=10) are the
common case for interactive search.

## Concurrent queries and the page cache

The saved index is read-only and shared by every query. Each query opens its own cursors, and each
disk cursor decodes into its own 128-posting buffer, so the search path takes no locks and only
small allocations reach the Go heap. Queries scale with cores until the hardware runs out: on the
Apple M3 (4 performance and 4 efficiency cores), BMW at k=10 went from 142.0 queries per second
with one client to 283.1 with 2, 479.6 with 4, and 684.5 with 8 (4.8x). Beyond 4 clients, queries
also run on the slower efficiency cores, and per-query p99 latency rose from 43.18 to 76.26 ms.

The page cache decides what those numbers mean:

- **Warm runs measure CPU, not disk.** The 973 MB MS MARCO index fits easily in 16 GB of RAM.
  `quarry-bench` runs one warm-up pass per algorithm and k first, so measured queries find their
  pages already cached, and the results say so.
- **Cold queries pay for page faults.** A page touched for the first time waits for a disk read;
  pruning helps here too, since a skipped block is never read. Cold-cache latency was not measured.
- **Mapped pages are outside Go's memory accounting.** They count toward the process's resident
  memory but not the Go heap or `GOMEMLIMIT`. They are clean, file-backed pages, so under memory
  pressure the OS drops them without swapping and rereads them on the next touch.
- **Opening reads the whole index once** to verify checksums, which also warms the cache. In
  `quarry-serve` this happens at startup, not on the first request.
- **An index larger than RAM** would make hot terms' blocks compete for cache space, and latency
  would then depend on query locality and disk speed. That case was not tested.

## Serving

`quarry-serve` opens one index at startup and serves `GET /search` and `GET /healthz` with Go's
standard `net/http`. Each request goes through these layers, outermost first:

1. **Server timeouts** stop slow or idle clients from holding connections: 5 s to send headers
   (against slow-header attacks), 10 s for the whole request, the request timeout plus 5 s to write
   a response, 60 s for idle keep-alive connections, and 16 KiB of headers.
2. **`http.TimeoutHandler`** gives each request `--timeout` (default 5 s) in total. When it fires,
   the client gets a 503 with a JSON body; the content type is set outside the handler so even the
   timeout response is JSON.
3. **Validation** rejects bad input with 400 before any work: `q` required, non-blank, at most 1000
   bytes; `k` from 1 to 1000; `algo` one of the three; each parameter at most once. Limiting query
   length and k bounds the cost of any single query.
4. **A semaphore** (a buffered channel of `--max-concurrent` slots, default twice the CPU count)
   limits searches running at once. A request waits for a slot only while its time limit allows,
   then gets 503 `server busy`. More searches than cores would only share CPU time and raise every
   query's latency.
5. **The search** runs with the slot held. `took_ms` covers analysis and search, not the wait.

**Search cannot be cancelled.** The query loops take no context, so a search keeps running after its
request times out. It also keeps its slot until it finishes, so the total work in flight never
exceeds `--max-concurrent` searches, even when clients give up and retry. The cost is that under
overload, a slot can be busy with a search nobody is waiting for. Checking for cancellation inside
the loops (say, once per decoded block) would fix that; it was left out because the slowest
measured query (exhaustive, p99 about 127 ms) is far below the 5 s limit.

**Shutdown waits for searches before unmapping.** On SIGINT or SIGTERM, `http.Server.Shutdown`
stops accepting connections and waits up to 10 s for responses. That is not enough on its own: a
search whose response already timed out is still running in the background, and unmapping the
index under it would crash the process, not return an error. Each handler holds a read lock while
it runs; shutdown takes the write lock, which waits for all of them, and only then closes the
index. Requests that arrive after that get 503.

Other choices: the server binds to `127.0.0.1` by default because it has no authentication; search
failures are logged to stderr and the client sees only `search failed`; and `HEAD` is accepted on
both endpoints for health checkers.

## Tradeoffs and what I would do next

The main tradeoffs, and what each one bought:

| Choice | Bought | Gave up |
|--------|--------|---------|
| Varint gaps inside 128-posting blocks | Simple, fuzzable codec; format 1's postings bytes unchanged | Smaller, faster bit-packed blocks (Lucene's choice) |
| Fixed-width sorted dictionary | Binary search straight on the mapping, nothing built at open | Space: an FST or front coding would shrink the 121 MB dictionary |
| One merged segment, immutable | Simple reads, global statistics are exact | Incremental updates: adding documents means rebuilding |
| Exact pruning | Results identical to exhaustive search, testable bit for bit | Approximate methods that skip more aggressively |
| Exact lengths, float64 scores | Simpler, more precise scoring | Byte-for-byte agreement with Lucene (nDCG@10 0.6777 vs 0.6789 on SciFact) |
| mmap on macOS and Linux | Small heap, fast open, shared page cache | Windows support, and control over what stays in memory |
| Uncancellable search | Simpler, faster inner loops | Freeing a slot as soon as a request times out |

What I would do next, in order of expected value:

1. **A bit-packed block codec** (PForDelta style). Decoding varints takes about 5.5 ns per posting
   and the postings are 629 MB; packing each block at a fixed bit width decodes with no branches
   per value and would shrink both the index and query time.
2. **Cancellable search**, checking the request context once per block, so timed-out requests free
   their slot.
3. **Incremental indexing** with a tiered merge policy: write new documents as small segments,

4. **Sharding** across processes with a scatter-gather frontend that merges each shard's top k.

5. **Phrase queries**, which need term positions in the postings.
6. **Measuring cold-cache and Linux behavior**, which the current numbers do not cover.
